# clingox design

_The design document for clingox 508.2. It records what the binding is, the safety
rules it follows (S1 to S20), and the reasons behind them. §12 lists the decisions
that shaped the scope._

## 1. What clingox is

A complete, safe, idiomatic Rust binding to clingo's C API, published on crates.io
for anyone, and kept current with clingo releases.

**Target:** clingo **5.8.2** (tag `v5.8.2`, commit `a99ffb2a`, released 2026-08-14).
Its C API (`libclingo/clingo.h`) exports **254 functions and 2 data tables**
(`g_clingo_ast_attribute_names`, `g_clingo_ast_constructors`).

**Platforms:** Linux, macOS, Windows, Android, iOS, and browsers through WebAssembly.
The browser route was proven by a spike; see §9.

**Not in scope yet:** clingcon and clingo-dl (separate libraries, possibly separate
crates later).

## 2. Pillars

Every decision below serves one of these. Each has a test that proves it.

| Pillar | Meaning | Proven by |
|---|---|---|
| **Correctness** | Same answers as clingo itself | Upstream conformance suite (§8) |
| **Safety** | No undefined behaviour reachable from safe Rust, including misuse, leaks, panics and threads | Rules S1–S20, sanitizers, compile-fail tests |
| **Determinism** | The same program and options give the same result on every run | Defaults (1 thread, fixed seed); a repeat-run test |
| **Resource limits** | A bad program cannot hang the caller or exhaust memory unnoticed | Timeouts, interruption, grounding-size guard (§6.5) |
| **Portability** | Builds and runs on every target in §8 | CI matrix |
| **Developer experience** | Reads like Rust; clingo users feel at home | docs, examples, API review |
| **Performance** | No avoidable copies in hot paths; measured | Benchmarks in CI (nightly) |
| **Supply chain** | The bundled C++ is exactly the upstream release | Commit-hash check, `cargo-deny`, SBOM |
| **Maintainability** | A clingo release becomes a clingox release quickly | Upgrade workflow (§9), COVERAGE.md |

## 3. Decisions at a glance

| Topic | Decision |
|---|---|
| Crates | `clingox-sys` (raw), `clingox` (safe), `clingox-derive` (proc macros); all share one version |
| License | MIT OR Apache-2.0 |
| Upstream source | git submodule `clingox-sys/clingo`, pinned to tag `v5.8.2`; CI checks the commit hash |
| Default build | vendored, static, built with the `cmake` crate, from a copy with small patches for upstream bugs Rust cannot fix (§5.5) |
| System library | opt-in through env vars; accepted range **`>= 5.8.1, < 5.9.0`** |
| Bindings | generated by bindgen, committed; CI fails if stale |
| Version | `508.2.0` = clingo 5.8.2, our release 0 (§10) |
| Version checks | build time (header macros) and runtime (`clingo_version()`), both accepting `>= 5.8.1, < 5.9.0` |
| Threads | Cargo feature `threads`: on for native targets; off by default for WASM, opt-in for cross-origin-isolated pages. `Control` is `Send`, never `Sync` (S12) |
| Errors | one `check()`; error state reset before each call; message copied on the calling thread |
| Leaks | no safety invariant depends on a guard's `Drop` |
| Panics | caught in every trampoline; resumed on the caller's thread |
| First release | `508.2.0`, only when complete. Pre-releases `508.2.0-alpha.N` |

## 4. Why our own binding

Every existing Rust binding (`clingo-sys` 0.7.2, `clingo` 0.8.0, `aspire` 0.5.3) is
built from the **5.6.2** header. Three changes since then break them when linked to
a current clingo (verified in both headers):

- `clingo_backend_theory_atom` and `..._with_guard` gained a sixth, out-parameter
  (5.7.0). An old caller makes clingo write through a garbage pointer.
- The theory sequence types swapped values: 5.6.2 `list = 1, set = 2`, 5.7.0+
  `set = 1, list = 2`. Lists and sets are silently exchanged.
- The AST parser emits `Comment` nodes (5.7.0), which exhaustive matches do not know.

clingo keeps `SOVERSION 4` throughout, so the dynamic loader cannot catch a
mismatch. Upstream promises no C API or ABI stability and labels breaks in minor
releases. The prior bindings also have soundness holes reachable from safe code
(research 02 §4, 03 §3.4).

## 5. `clingox-sys`

### 5.1 Getting clingo

- **Vendored (default feature `vendored`).** At tag v5.8.2, clasp, libpotassco and
  `third_party/` are ordinary directories, so a plain submodule checkout is complete.
  Nothing is downloaded at build time. The build compiles a patched copy of the
  submodule (§5.5).
- **System (opt-in):**
  - `CLINGO_LIB_DIR`, `CLINGO_INCLUDE_DIR`, `CLINGO_STATIC=0|1`;
  - `CLINGO_THREADS=0|1` says whether that clingo was built with threads (unset
    means 1, the default of clingo's CMake build), since the installed library does
    not record it;
  - `CLINGOX_SYS_NO_VENDOR=1` forces the system path even when a dependency enabled
    `vendored`, because Cargo features are additive;
  - build.rs reads `CLINGO_VERSION_*` from the found header and refuses anything
    outside `>= 5.8.1, < 5.9.0`. **5.8.0 is refused** because concurrent symbol
    creation became safe only in 5.8.1 (#617), and S9 relies on it;
  - pkg-config is a best-effort fallback only, since clingo installs no `.pc` file;
  - build.rs emits `rerun-if-env-changed` for each variable and never panics just
    because a variable is unset.

### 5.2 Building it

CMake options:

```
CLINGO_BUILD_STATIC=ON   CLINGO_BUILD_SHARED=OFF   CLINGO_BUILD_APPS=OFF
CLINGO_BUILD_WITH_PYTHON=OFF  CLINGO_BUILD_WITH_LUA=OFF   (both default to auto)
CLINGO_MANAGE_RPATH=OFF  CLINGO_INSTALL_LIB=ON
CLASP_BUILD_WITH_THREADS=ON|OFF           (follows the `threads` feature)
CMAKE_POSITION_INDEPENDENT_CODE=ON        (a static build is not PIC otherwise)
CMAKE_DISABLE_FIND_PACKAGE_BISON=ON       (use the committed parsers; a host
CMAKE_DISABLE_FIND_PACKAGE_RE2C=ON         bison would otherwise regenerate them)
CMAKE_BUILD_TYPE=Release                  (even for debug Rust builds)
```

(`CLINGO_BUILD_TESTS`/`EXAMPLES` already default to OFF, and `CLASP_BUILD_APP`
follows `CLINGO_BUILD_APPS`, so none of them is set.)

Adopted from z3-src:
- the MSVC runtime follows `crt-static`;
- `.lib` vs `.a` naming follows `target_env`;
- `lib`/`lib64` probing;
- compiler launchers are forwarded for sccache, and, opt-in only, for ccache.

**Compiler caching (`forward_compiler_launcher`).** sccache is picked up
automatically whenever it already wraps rustc (`RUSTC_WRAPPER`), since that is
already an explicit choice by the caller. ccache is opt-in only: `clingox-sys`
is a published crate, so its build script must not start reaching outside the
build just because `ccache` happens to be on a user's `PATH`. Set
`CLINGOX_SYS_CCACHE=1` or `=auto` to use whatever `ccache` is found on `PATH`,
or to an explicit path to use that binary; either fails loudly if the
requested `ccache` cannot be used. `0`, empty or unset (the default) never
reaches for ccache. Either way this sets
`CMAKE_C_COMPILER_LAUNCHER`/`CMAKE_CXX_COMPILER_LAUNCHER` rather than relying
on a `PATH` symlink in front of the real compiler, so it reaches the host
compiler, the Android NDK's clang and Emscripten's `emcc`/`em++` alike, and
keeps working even when `CC`/`CXX` name the real compiler by an absolute path
that bypasses such a symlink. `cargo xtask` sets `CLINGOX_SYS_CCACHE=auto` for
every build it drives when `ccache` is present (`xtask/src/util.rs`,
`use_ccache_if_found`), so clingox's own workflow gets the speedup without a
downstream build being affected (TESTING.md, "Build speed").

**Link lines:**
- **`clingo gringo reify clasp potassco`**, all five. They are linked as `static`,
  which Rust bundles into the `clingox-sys` rlib as one archive, and linkers rescan
  a single archive until it resolves, so the order between them does not matter
  (verified with both lld and GNU ld). What matters is that none is missing:
  libgringo and libclingo both use libreify.
- The C++ runtime, using the `cc` crate's table: none on MSVC, `c++` on Apple and
  BSD, `c++_shared` on Android, `stdc++` elsewhere, overridable by `CXXSTDLIB`.
- `pthread` on Unix when `threads` is on, and `atomic` where clasp's CMake asks for it.

A static build defines `CLINGO_NO_VISIBILITY` publicly. Binding generation defines
it too, so Windows symbols are not declared `dllimport`.

### 5.3 Bindings

- `xtask bindgen` runs a pinned bindgen over the vendored `clingo.h`, with
  `--rust-target` set to the MSRV, and writes `src/bindings.rs`. CI regenerates and
  runs `git diff --exit-code`; the diff doubles as the API diff for each clingo bump.
- Users never need libclang.
- The raw layer stays raw; nullability and ownership are handled once, in `clingox`.
- `systest` (rust-lang `ctest` 0.5) checks every signature, layout and constant
  against the real header on each platform that runs tests. It is also what proves
  that one bindings file is valid on every target.

### 5.4 Metadata and packaging

- `links = "clingo"`. clingox-sys therefore cannot share a dependency graph with
  Potassco's `clingo-sys`, which is correct because the C symbols would clash. The
  README says so.
- Exported to dependents: `DEP_CLINGO_VERSION`, `DEP_CLINGO_INCLUDE`,
  `DEP_CLINGO_ROOT`, `DEP_CLINGO_VENDORED`, `DEP_CLINGO_THREADS` and
  `DEP_CLINGO_PATCHES` (the UPSTREAM-ISSUES entries patched in, comma-separated).
- `pub const CLINGO_VERSION: (u32, u32, u32) = (5, 8, 2)`, generated from the header.
- `pub const HAS_THREADS: bool`, `VENDORED: bool` and `PATCHES: &[&str]`, written by
  build.rs for what it actually built or found. `clingox` takes its thread support
  from `HAS_THREADS`, never from the target, so a system clingo without threads is
  refused with `Unsupported` rather than failing inside clingo.
- **Package with an `include` allowlist:**
  - in: the sources, headers and CMake files of libclingo, libgringo (with `gen/`),
    libreify, clasp and libpotassco, the header-only `third_party` libraries, and
    every license file;
  - out: Catch, tests, examples, apps, and the Python and Lua bindings;
  - the measured pruned tree is 1.26 MB compressed; CI asserts the file list and an
    8 MB ceiling;
  - `THIRD-PARTY-LICENSES` covers MIT, BSL-1.0 and CC0;
  - an SBOM lists the bundled components and the upstream commit.
- docs.rs: when `DOCS_RS` is set, build.rs skips the native build and emits no link
  lines.
- The `include` list also carries `patches/*.patch`.

### 5.5 Patches to the vendored source

Some upstream bugs cannot be fixed from Rust: a signal kills the process before any
Rust code runs, a static destructor runs after `main`, and a race between clasp's
own threads happens inside a single clingo call. They are fixed by small
patches in `clingox-sys/patches/`, one per `docs/dev/UPSTREAM-ISSUES.md` entry, whose
number starts the file name (RULES 8, decided 2026-09-27):

- `U1-division-traps.patch`: `INT_MIN / -1`, `INT_MIN \ -1` and a term's `x \ 0`
  are undefined, like a division by zero, instead of raising SIGFPE;
- `U2-leak-symbol-table.patch`: the symbol table is allocated once and never
  destroyed, so symbols stay valid while static destructors run;
- `U19-statistics-type-registry.patch`: clasp's registry of statistic types is a
  fixed array under a mutex, so controls on several threads can register and read
  statistics at once (S12).
- `U35-external-rewrite-arithmetics.patch`: `#external` keeps the replacement
  that arithmetic rewriting returns for its atom and type term, instead of a
  term with moved-out operands that crashes the next pass.
- `U46-app-finish-without-threads.patch`: the application's control forwards clasp's
  step-ready event to the solve event handler in builds without threads too, so
  `on_statistics` and `on_finish` are delivered on WebAssembly without atomics, as
  they are for a library control.
- `U47-ast-refcount-overflow.patch`: `AST::incRef` aborts instead of wrapping when the
  32-bit count is at its maximum, so no safe sequence of clones frees a live node.
- `U49-range-binder-int-max.patch`: the grounder's range binder stops after it has
  produced `INT_MAX` instead of incrementing past it.
- `U50-parallel-split-leak.patch`: clasp's shared data for a parallel search frees the
  guiding paths still queued when it is destroyed, which a search stopped in splitting
  mode left behind.

**Mechanism.** build.rs copies the part of the submodule that CMake reads (the list
mirrors the `include` allowlist) to `$OUT_DIR/clingo-patched`, keeping the layout,
applies the patches in file-name order with its own applier, and runs CMake on the
copy. The applier is Rust code, because hosts such as Windows or an NDK host may
lack `patch` and `git`; hunks must match at their stated line, context included,
and a patch that does not apply fails the build with its name and the hunk. A file
is written only when its content changes, so an unchanged copy keeps its
timestamps. The submodule is never written: the commit-hash check still passes, and
`clingox-sys/tests/patches.rs` checks that the copy differs from it exactly in the
files the patches name.

Each patch is a `git diff` against the tag, at most 40 changed lines, with a header
that names its issue and why, so it can be sent upstream as it is. A system library
gets no patch; the guide says which bugs remain there. A patch is removed when the
clingo release clingox binds contains the fix (UPGRADING §1.5).

## 6. `clingox`: rules

### 6.1 Errors

- **S1. One error path.**
  - Before each fallible C call, the thread-local error state is reset with
    `clingo_set_error(clingo_error_success, "")`. clingo never resets it on success,
    so without this a bare `false` would report a stale error.
  - After a `false`, `check()` first consults the callback slot (S6), then reads
    `clingo_error_code()`, and **copies** the message at once. The buffer is
    overwritten by the next message query or failure on that thread
    (`libclingo/src/control.cc:113-225`).
  - A `false` with a success code maps to `Unknown("no message")`.
  - **Not every `bool` return is a success flag.** `clingo_symbol_is_equal_to`,
    `clingo_signature_is_*`, `clingo_assignment_*` predicates,
    `clingo_control_is_conflicting`, `clingo_ast_equal` and similar return values.
    COVERAGE.md classifies each function, and only success flags go through `check()`.
- **S2. `Error` and `ErrorKind`.**
  - `Error` is `Send + Sync + 'static`, with `kind()`, `Display` holding clingo's
    copied message, and `source()` holding a user's own error.
  - `ErrorKind` is `#[non_exhaustive]`: `Parse`, `Runtime`, `Logic`, `BadAlloc`,
    `Unknown`, `Callback`, `Conversion`, `Utf8`, `Nul`, `Poisoned`, `Version`,
    `Unsupported`, `InvalidInput`, `GroundingLimit` (S15). `Unsupported`
    covers a feature the build lacks, such as async solving without threads,
    which clingo reports as a logic error that would otherwise poison the
    `Control`. `InvalidInput` is input clingox rejects before calling clingo (a
    reserved part name, a thread count outside 1 to 64); a NUL byte stays `Nul`.
    Neither poisons. `GroundingLimit` is entirely clingox's own construct (no
    clingo error corresponds to it), and unlike every other kind clingox itself
    detects, it does poison (see the poisoning rules below). An interrupt or a timeout is a
    search result, never an error.
  - **Parse errors carry their messages.** During `add`, `load` and `parse_term`,
    clingox captures clingo's log messages internally and attaches them to the error,
    with locations. They are also forwarded to the user's logger or the `log` crate.
  - `Error::callback(e)` wraps any `std::error::Error + Send + Sync` from user
    callbacks. Its `Display` names the operation only (`the callback failed`,
    after the context); the user's error is the source, so a reporter that walks
    the chain prints its text once. `Error::conversion(message)` is the
    `Conversion` error for hand-written `ToSymbol` and `FromSymbol` impls.
- **S3. Poisoning.** After a non-recoverable error (`H:136-139`), the `Control`
  answers only `Err(Poisoned)`, and `Drop` still frees it.
  - **Recoverable (not poisoning):** conversion, UTF-8 and NUL errors raised
    on the Rust side, and version errors.
  - **Poisoning until proven otherwise:** `Logic`, `BadAlloc`, `Unknown`, and a failed
    handle close.
  - **Poisoning, settled:** a `Parse` error from `add`. clingo cannot ground the same
    control after one (seen in the WASM spike), and a test covers it.
  - **Poisoning: an error or panic that stops grounding partway.** This
    covers a failed or panicking ground callback (`Control::ground_with`), a
    failed or panicking
    [`GroundProgramObserver`](crate::observer::GroundProgramObserver) callback,
    and [`ErrorKind::GroundingLimit`] (the grounding-size guard, S15). This
    case is not treated as recoverable, although clingo's own tests keep using
    a `Control` after a failed callback
    (`libpyclingo/clingo/tests/test_control.py:98-108`). That a test keeps
    running is not evidence the *result* it then computes is correct: checked
    directly with pyclingo 5.8.2, an observer raising at
    the third rule of `a. b. c. d. e :- d.` leaves a control whose solve
    returns `a b`, and a later `add`/`ground` of `d e a b`, so `c` is lost for
    good and never comes back; a ground callback failing partway through
    `p(1..4). q(X) :- p(X), X = @f(X).` leaves a control that would answer
    `p(1) .. p(4) q(1) q(2)` if solved, `q(3)`/`q(4)` never added. clingo
    keeps whatever it already ground and answers from that truncated program
    silently, with no flag or error marking it incomplete: this is not a
    result a caller can safely receive, whatever kind of error caused it, so
    it poisons unconditionally, and recovery means building a new `Control`.
    `clingox/tests/api_ground_callbacks.rs`, `api_observer.rs` and
    `api_grounding_limit.rs` test this for all three sources.
  - **Poisoning: the same observer failure, outside grounding.** A registered observer callback can still fire
    through `Control::with_backend` (a directive added inside its closure, or
    a fact's delayed notification at the backend's own close) and through
    every entry point that starts a search (`end_step` fires when a solve
    starts, not only when grounding finishes). clingo has already passed
    part of the output on by the time the observer stops it, the identical
    hazard the row above already poisons for, so these poison
    unconditionally too, with the observer's own error unchanged and its
    panic's payload untouched, no added context.
    `clingox/tests/observer_errors_outside_ground.rs` tests this.
  - Open question: a backend writer
    (`Control::register_backend_writer`) that fails to write partway through a
    later `ground`, for example on a full disk, may leave the same kind of
    truncated program. Such an error reaches clingox as an ordinary
    `ErrorKind::Runtime` from `ground`, which does not poison. It is not
    tested yet; decide it when a way to provoke the failure is found.
  - clingo 5.8.2 reports an unknown command-line option as `clingo_error_logic`,
    although `clingo.h` documents `clingo_error_runtime`. clingox follows the
    library's behaviour, and a test pins it.

### 6.2 Ownership and lifetimes

- **S4. Leaks are safe.** `mem::forget` is safe Rust, so no invariant may depend on
  a guard's `Drop`. `Control` records, in interior-mutable state:
  - the active solve handle and its boxed event handler;
  - whether a backend or program builder is open, in two separate flags
    (`ControlHandle::backend` and `::builder`). A program builder session left
    open is not harmless: clingo grounds and solves an empty program without
    an error, and a text `add` drops part of the session (U37). So the builder
    flag is closed wherever the backend's is, by `finish_search` and by
    `ControlHandle::drop`, and `with_program_builder` clears it before it
    opens a session. What a closure added before it failed or panicked is
    kept.

  **Every entry point, `&self` included, first finishes any leftover.** A forgotten
  async solve would otherwise keep running while `statistics()` reads clasp state,
  which the header forbids (`H:2981-2983`). This includes `is_conflicting`
  and the `enable_*` getters (`&self`; "clingo cannot fail this query" is no
  reason to exempt them), and `finish_search` itself
  collects a registered observer's own error or panic right after closing
  a leftover backend, instead of leaving that check to whichever caller
  happens to read the observer slots next.
- **S5. Borrow, don't consume.**
  - `SolveHandle<'c>`, `Backend<'c>`, `ProgramBuilder<'c>` and `Configuration<'c>` hold
    `&'c mut Control`.
  - `SymbolicAtoms<'c>`, `TheoryAtoms<'c>` and `Statistics<'c>` hold `&'c Control`, so
    `ground` and `solve` are statically impossible while they are alive.
  - Handles are `NonNull<ffi::T>` plus a lifetime, never `&mut` to an opaque struct.
- **S6. Lending models.**
  - `next_model(&mut self) -> Result<Option<&Model>>`: a model dies when the search
    resumes, so it cannot be a plain `Iterator`.
  - `Model::snapshot()` produces an owned `OwnedModel`.
  - Only models delivered to the solve-event callback offer `extend`
    (`H:2435`); they are a distinct type.
- **S7. Solve handle semantics** (`H:2566-2643`, `control.cc:1379-1402`):
  - `get()` waits for and returns the `SolveResult`;
  - `close()` = `get()`, then `clingo_solve_handle_close`, returning the result;
  - leaving a model loop early = `cancel()`, `get()` (the result says
    `interrupted`), then close;
  - `Drop` only closes, which cancels.
  - A solve without yield or async runs entirely inside `clingo_control_solve`, so
    that is where it blocks.
  - **A `SolveEventHandler`'s own failure recorded by a drop-triggered close
    is discarded, not promoted.** `close()`
    is the deliberate, caller-initiated close that reports it; `Drop`, and
    every other path that closes a search only because it happens to be a
    leftover (a forgotten handle's search, closed by the next entry point,
    S4), discard it along with the handler instead. Promoting it there would
    have it surface later from whatever unrelated call reads the
    control-level slots next, and blame that call: `raw::ControlHandle::
    close_active`'s `promote_handler` flag is `true` only for `get_and_close`
    (behind `close()`) and a blocking search's own in-place close right
    after it runs (`solve_with_handler`); every other caller of
    `close_active`/`close_solve` passes `false`.
    `clingox/tests/solve_events_drop.rs` tests this.

### 6.3 Callbacks

- **S8. Every trampoline:**
  - is `extern "C"` and runs inside `catch_unwind`;
  - uses a NULL-safe slice helper (`from_raw_parts(NULL, 0)` is UB);
  - on **every** `false` return, calls `clingo_set_error` first;
  - stores the typed error or panic in a first-writer-wins atomic slot **in the
    callback context**, never in thread-local storage, because callbacks run on
    solver threads (the one exception is script callbacks, S20);
  - makes every later callback return `false` at once once the slot is set;
  - hands the error or panic to the API method, which returns it or resumes the
    panic on the caller's thread.

  clingo's own code and message after a callback failure are never trusted over the
  slot: parallel solving rewrites them, and async solving loses them.

  **Every entry point through which clingo can call a registered observer
  reads its slot afterward, not only `Control::ground`/`ground_with`**
  (`resolve_ground` alone is not enough). The full list, with the clingo source lines that prove
  each, is in the rustdoc of
  [`GroundProgramObserver`](crate::observer::GroundProgramObserver); in
  summary: `Control::ground`/`ground_with` (`clingo_control_ground`);
  `Control::with_backend`, twice (synchronously inside its closure, for a
  directive such as `add_rule`, and once more at `clingo_backend_end`, for a
  fact's delayed notification); and every entry point that starts a search
  (`Control::solve`, `solve_yield[_with_events]`, `solve_async[_with_events]`,
  `solve_with_events`), because `end_step` fires when a solve starts
  (`ClingoControl::solve` -> `prepare` -> `out_->endStep`,
  `clingocontrol.cc:437-438, 558-561`), not only when grounding finishes. An
  observer's error poisons the control unconditionally wherever it is read,
  and its panic's payload resumes untouched, exactly as `ground`'s already
  did (S3 above).
- **S9. Void callbacks** (the logger, propagator `undo`, script `free`) cannot report
  failure. A panic there is recorded in the slot, and the next callback that can
  return `false` does so.
- **S10. Where callbacks run, and what they may capture:**

  | Callback | Runs on | Bound |
  |---|---|---|
  | ground functions (`ground_with`) | caller's thread | borrowed `FnMut` |
  | `for_each_model` | caller's thread: built on the yield handle, never on clingo's model event | borrowed `FnMut` |
  | AST parse callback | caller's thread | borrowed `FnMut` |
  | logger | any thread | `Send + 'static`, owned by `Control` |
  | solve-event handler (`solve_async`) | solver threads | `Send + 'static`, owned |
  | observer | caller's thread during ground | `Send + 'static`, owned |
  | propagator | several solver threads, re-entrantly | S11 |

  With `parallel_mode > 1`, clingo's model event runs on the worker that found the
  model (`clasp/src/parallel_solve.cpp:654-683`). That is why `for_each_model` uses
  the yield handle instead. A runtime test with 4 threads and a `!Send` capture
  proves the closure never leaves the caller's thread.
- **S11. Propagators.** clasp **releases its own lock** inside `add_clause`,
  `propagate`, `add_watch` and `add_literal` (`clasp/src/clingo.cpp:111-127,
  230-243, 311-320`), and the design must stay sound whether or not clasp
  calls `undo` back on the same thread while `propagate` is still on the
  stack: **soundness here never depends on which way that goes.** A Rust
  `Mutex` around `&mut self` would deadlock if that reentrancy occurred and
  clingox tried to guard against it with a lock of its own, and `&mut self`
  without one would alias if it occurred. So:
  - one trait, `Propagator: Send + Sync`, with **`&self`** methods;
  - state lives in interior-mutable containers the user chooses (an atomic, a
    `OnceLock`, or a `Vec` sized from `PropagateInit::number_of_threads` and indexed
    by `PropagateControl::thread_id` for state touched by one solver thread at a
    time). No `PerThread<T>` convenience ships in the crate: pairing an
    `init(&self)` that sizes shared storage with a `get(&self) -> &T` read from
    arbitrary solver threads is its own hand-rolled synchronisation primitive,
    and deserves its own contract rather than riding in as a small
    registration/watches helper;
  - the docs state the one rule users must keep: **never hold your own lock across a
    call into `PropagateControl`**, since a future clasp version could re-enter
    `undo` on the same thread even though the currently vendored one does not
    (see the reentrancy notes below);
  - after clingo signals stop (`add_clause` or `propagate` returning false), the
    control object refuses further calls without touching C.

  A deferred-undo alternative (queue re-entrant `undo` until `propagate` returns) is
  kept in reserve. Tests force backjumps with 1, 2 and 8 threads, and pass under TSan.

  **Registration, `init`, watches, and the dispatch wiring for all five callbacks.** `init` runs once per solving step, from
  `ClingoPropagator::init` (`clasp/src/clingo.cpp`), called from `prepare`
  before `solveParallel`'s thread pool exists (`clasp/src/parallel_solve.cpp`);
  it is therefore never concurrent with itself or with `propagate`/`undo`/
  `check`/`decide`, and needs no `Sync`-sensitive locking of its own beyond the
  trait bound. All five of `ClingoPropagator`'s C++ adapter methods
  (`libclingo/src/control.cc:2088-2124`) throw an ordinary `ClingoError()` on a
  `false`/void return from the registered `clingo_propagator_t` callback,
  caught by the same `catch`/error-propagation path every other clingo error
  uses; none of them calls `clingo_terminate`/`_Exit`, unlike three of the four
  solve-event callbacks (U25). A `ClingoError()` thrown from `init` is caught
  by `ParallelSolve::solveParallel`'s own `try` block
  (`clasp/src/parallel_solve.cpp:429-452`), so no uncaught C++ exception
  reaches `std::terminate` for this callback family. `register_propagator`
  itself only copies the `clingo_propagator_t` struct of function pointers by
  value into clingo's own `ClingoPropagator` wrapper
  (`libclingo/src/control.cc:2136-2140`); the Rust-side context (the
  propagator plus its error/panic slots) is boxed once at registration and
  kept in `ControlHandle::propagators` until after `clingo_control_free`,
  mirroring `ControlHandle::observers`' own ownership shape.

  **Soundness never depends on whether reentrancy
  actually occurs, and it currently does not.** It is tempting to conclude that
  clasp "can call back into that same propagator's
  `Propagator::undo`, on the same OS thread, with `propagate`'s own call to
  `add_clause` still on the stack," reading `ClingoPropagator::Control::
  addClause` (`clasp/src/clingo.cpp:111-116`) as always reaching
  `pp->addClause(solver(), state_)`'s own `s.undoUntil(dl)` branch
  synchronously when the added clause conflicts below the current level.
  **This is not so for the vendored clasp build, as direct
  instrumentation showed**: `ClingoPropagator::Control`'s own constructor
  (`clingo.cpp:93`, `state_(st | state_ctrl)`) unconditionally ORs
  `state_ctrl` into every `Control` object clasp ever builds, including the
  one handed to `Propagator::propagate`. `ClingoPropagator::addClause`'s own
  `if ((st & state_ctrl) != 0u) { return false; }` (`:332`) therefore always
  fires *before* `s.undoUntil(dl)` on every call reachable from
  `PropagateControl::add_clause`, regardless of the clause's own shape or
  decision level; `s.undoUntil(dl)` is reachable only from
  `propagateFixpoint`'s own, separate, non-nested loop-bottom call
  (`addClause(s, state_prop)`, `:292`, a direct member call that never
  constructs a `Control` object at all). `PropagateControl::propagate`
  (structurally different: no `state_ctrl` guard, calls `solver().
  propagateUntil` directly) was also tried: it can reach a genuine conflict
  synchronously inside the call, but that conflict's *resolution* (the
  backjump and the `undo` calls that go with it) is deferred to clasp's own
  outer conflict-analysis loop the same way `add_clause`'s is, never nested
  inside the call either. **No fixture using `PropagateControl::add_clause`
  or `propagate` can reach a synchronous `undo` in this clasp build**; the
  gate is on which C++ object made the call, not on anything a Rust-level
  fixture can control about the clause.

  **This does not weaken the design, because the design was never resting
  on it.** `Propagator: Send + Sync` with every method `&self`, state kept
  in interior-mutable containers the user chooses, and "never hold your own
  lock across a call into `PropagateControl`" together make *either* outcome
  sound: a reentrant `undo` on the same thread (if a future clasp version
  ever takes the `state_prop`-only path from inside a callback), or the
  non-reentrant behaviour actually observed. `&self` costs nothing when
  reentrancy does not happen, and interior mutability (an atomic, a
  `OnceLock`, or a `Cell`/`RefCell` behind per-thread indexing) tolerates it
  without deadlocking if it ever does; no lock of clingox's own
  (`PropagatorContext::run`/`run_void` in `clingox/src/raw/propagate.rs`
  hold none, and neither does any wrapper type between the trampoline and
  the user's callback) is ever held across a call into `PropagateControl`
  either way. The `state_ctrl` mechanism above is recorded here as the
  current, directly-checked evidence for *why* reentrancy does not occur
  today, not as something clingox's own soundness depends on: that evidence
  could change with a future clasp version without requiring any change to
  this design.

  `clingox/tests/propagator_reentrancy.rs`'s forced-backjump test pins the
  currently-observed behaviour directly (a per-thread "currently inside
  propagate" flag `undo` checks against): `undo` fires, but never while
  `propagate` is still on the same thread's own call stack, at 1, 2 and 8
  threads. The data-race probe alongside it exercises the same
  `PropagateControl` surface (`add_clause`, `add_watch`, `has_watch`,
  `remove_watch`) concurrently across solver threads. Both pass under
  `cargo xtask sanitize`'s thread sanitizer at 1, 2 and 8 threads, zero
  warnings (the criterion for calling this design final).

### 6.4 Threads

- **S12. Thread rules:**
  - `Symbol` and `Signature` are `Copy + Send + Sync + 'static`. Symbols live in a
    global table that is never freed, not even at exit in the vendored build (patch
    U2; a system clingo destroys it when the static destructors run). The table
    grows without bound, which is documented.
  - `Ast` is `Rc`-like and `!Send + !Sync`, because its reference count is not atomic.
  - `OwnedModel`, `Error`, `StatsTree` and `SolveResult` are `Send + Sync`.
  - **`Control` is `Send`, never `Sync`** (a settled decision). A source review
    searched libclingo, libgringo, clasp and libpotassco for thread-local
    and thread-affine state and found only clingo's error state, which clingox sets
    and reads within one call (S1), and clasp's per-thread CPU timers, which only
    make the reported CPU time span threads. The logger data is a heap address and
    the user logger is already `Send`. A control moved through every phase
    (created, added, grounded, solved, models of a yield search read on alternating
    threads, an async search waited for on one thread and read on another, dropped
    on another) ran clean under ThreadSanitizer with 1, 4 and 8 solver threads;
    `tests/api_threads.rs` repeats it under `cargo xtask sanitize`. One
    `unsafe impl Send for ControlHandle` records this. `SolveHandle` and
    `AsyncSolveHandle` are `Send` through `&mut Control`. `Model`, `Statistics`,
    `SymbolicAtoms`, `SymbolicAtomIter` and `Configuration` stay `!Send`: they are
    views that stay on their thread.
  - **Known upstream race (U11):** every `LogicProgram` shares clasp's static
    `Clasp::Asp::trueAtom_g`, and `ReduceParams::prepare` writes into the shared
    default configuration `config_def_s`, so separate `Control`s on separate threads
    race in clasp itself. A source review read every write: each stores the value already
    present, or a flag bit that no reader consults for this node
    (`logic_program.cpp:169, 172, 1017`), and 33,600 concurrent solves matched a
    single-threaded reference exactly. clingox therefore takes **no process-wide
    lock**; the race is reported upstream.
  - **Known upstream race, patched (U19):** clasp registers each kind of statistic
    in a global vector the first time it is used, without a lock, while other
    threads read it. Unlike U11 this can free memory under a reader, so it is fixed
    by patch U19 (§5.5), not suppressed; `tests/patch_u19_statistics_registry.rs`
    fails under ThreadSanitizer without the patch. A system clingo keeps the race.
  - **Known upstream race (U20):** `UncoreMinimize::initLevel` reads clasp's
    shared optimum level by level with none of the generation check its sibling
    readers use, so a mixed-generation read is possible in principle during
    multi-threaded core-guided optimisation (`--opt-strategy=usc`). A
    differential run against a single-threaded reference found 0 mismatches in
    1,968 runs; `tests/threads_optimisation.rs` repeats a scaled-down version
    of that check under `cargo xtask sanitize`, with real conflicts, which
    turned out to reach four more unsynchronized accesses in the same
    machinery: the retrying (and otherwise sound) read in
    `DefaultMinimize::integrateBound`, `UncoreMinimize::valid`'s own unchecked
    "maxBound" read (found in the same evidence as `initLevel`), and
    `Enumerator::optimize` and `commitUnsat`, which run unlocked because the
    only `Enumerator` this clasp ships never asks `ParallelSolve::commitUnsat`
    for its lock during optimisation (see UPSTREAM-ISSUES U20). All five are
    suppressed on the same differential evidence, not patched; the workaround
    if a wrong optimum is ever seen is `--opt-strategy=bb` or one thread.
  - **Known upstream race (U21):** `ShortImplicationsGraph::add` increments a
    plain `uint32` clause-count statistic with no lock while several solver
    threads share a short clause at once; found writing the U20 test above,
    which is the first thread test to make two solvers learn and share a
    clause at the same instant. The clause itself is still added through the
    atomic-based `Block` the shared list actually uses (`shared_context.h`);
    only its own count of itself can be lost, in the same relationship to that
    atomic design that U11's benign writes have to `trueAtom_g`.
  - **ThreadSanitizer suppressions** (`xtask/tsan-suppressions.txt`) name only
    clasp's known races, never clingox or Rust code: `Clasp::Asp::trueAtom_g` and
    `Clasp::ReduceParams::prepare` (U11), the two writes an interrupt makes
    while solver threads run, `Clasp::SequentialSolve::doInterrupt` (`term_`) and
    `Clasp::mt::ParallelSolve::doInterrupt` (the `syncT` timer) (U12, see
    `ControlPtr` in `raw/interrupt.rs`), `Clasp::UncoreMinimize::initLevel`,
    `Clasp::DefaultMinimize::integrateBound`, `Clasp::UncoreMinimize::valid`,
    `Clasp::Enumerator::optimize` and `Clasp::Enumerator::commitUnsat` (all
    U20), and `Clasp::ShortImplicationsGraph::add` (U21).
- **S13. Interrupts** (`clasp/src/clasp_facade.cpp:474-478, 322`):
  - clingo **queues** an interrupt sent while nothing is solving and kills the *next*
    solve at its start. So `InterruptHandle::interrupt()` acts only while a solve is
    active. It checks a shared "solving" flag under the same lock the `Control` takes
    around `solve` and `free`. Otherwise it returns `false` and does nothing.
  - That lock also makes interrupt-after-free impossible.
  - **Grounding cannot be interrupted**; the docs say so, and §6.5 covers it.
  - **How it is built:**
    - one lock is shared by the `Control` and every `InterruptHandle`, and guards a
      phase: `Starting`, `Running` or `Idle`;
    - `clingo_control_interrupt` is called only under that lock, in `Running`;
    - an interrupt during `Starting` is held and delivered once the search runs;
    - clingo's finish event sets `Idle` and must take the lock first. clasp reports
      it before it marks the search done, so a search cannot end while an interrupt
      is in flight;
    - `Drop` clears the control pointer under the lock.

    This was verified with about 400,000 racing solves and ThreadSanitizer.
  - **An interrupted result is never conclusive.** clingo 5.8.2 can report
    "unsatisfiable, exhausted" for an interrupted search of a satisfiable program
    (1,460 of 20,000 runs with an interrupting thread; reproduced in Python). So
    `SolveResult` reports an interrupted search as unknown, never as unsatisfiable or
    exhausted, and the raw clingo flags are available under a name that says they
    are not trustworthy after an interrupt.

### 6.5 Resource limits and determinism

- **S14. Time.**
  - `solve_async()` returns a handle with `wait(Duration) -> bool`.
  - `SolveOptions::timeout(Duration)` interrupts the solve when the budget is spent;
    the result reports `interrupted`.
- **S15. Grounding size.** Grounding cannot be interrupted, so the guard is
  cooperative. An optional observer counts ground atoms and rules, adding each
  callback's own contribution before checking the limit, so the callback that
  pushes a count over it is itself refused, whatever callback comes after it
  (a version that checked
  before counting left a violation on the grounding's last callback unreported
  by `ground_with_limit` itself). The refusal aborts grounding with an error
  whose kind is `ErrorKind::GroundingLimit`. Whether clingo aborts cleanly from an
  observer error is checked in §11.
- **S16. Determinism.**
  - Default options: one solver thread and a fixed seed.
  - Parallel solving is opt-in (`--parallel-mode=N`) and documented as
    non-deterministic in model order.
  - A CI test runs the conformance suite twice and compares the results.

### 6.6 Conversions, types and API hygiene

- **S17. No `transmute` on C values.**
  - C enums become `#[non_exhaustive]` Rust enums converted with `TryFrom`, mapped
    from bindgen constants, never from literals.
  - Unknown AST types map to `Other(i32)`.
  - Bitsets are clingox's own newtypes over clingo's bits, with `|`, `|=` and
    `contains`, as `ShowType` is (`bitflags` would be a public dependency and
    would let users build unknown bits). `clingo_backend_type_t` gets a hand-written
    type.
  - Out-parameters are allocated in Rust. Size-query-then-fill pairs become one call.
    Every wrapper has at least one test.
  - Separate id spaces get newtypes: `Atom`, `ProgramLiteral`, `SolverLiteral`, `Id`.
    Theory-atom `Id`s are reused after each solve (`H:726-730`), and the docs say so.
  - The **AST builder** `clingo_ast_build` is the only variadic function in the header,
    and the only way to create a node. It is never public. Generated typed
    constructors call it with the exact promoted C types per attribute, and each one
    is tested under ASan.
- **S18. Future-proofing and process-global effects.**
  - Public enums are `#[non_exhaustive]`; public structs have private fields;
    extension traits are sealed; no `Result` alias is glob-exported.
  - `clingox-derive` is pinned with `=` and generated code goes through
    `::clingox::__private`, as serde does.
  - **Runtime version check.** The first use of *any* clingox function (behind a
    `Once`) checks `clingo_version()` against the same range the build accepts,
    `>= 5.8.1, < 5.9.0`, and returns `Err(Version)` outside it. 5.8.1 is the floor
    because symbol creation became thread-safe there; 5.8.1 and 5.8.2 have the same
    C API. (An exact-patch check made a 5.8.1 system library
    build and then fail every call.)
  - **`clingo_main`** sets a process-wide singleton, installs signal handlers
    and never removes them, and can `_exit` on a signal, on `--time-limit` and on
    `--fast-exit` without unwinding (`clasp/libpotassco/src/application.cpp`;
    measured while building the application layer). `Application::run`
    (`raw::process` and `raw::application`) contains what can be contained:
    - **One run at a time, never a wait.** A process-wide `AtomicBool` is taken with
      one non-blocking attempt; a second `run` (nested, concurrent, or started from
      a callback on a solver thread) is `InvalidInput` at once, so no deadlock is
      possible by construction. It is released by a drop guard on every exit path,
      including a resumed panic.
    - **Signal dispositions.** The nine signals clasp changes (SIGINT, SIGTERM,
      SIGUSR1, SIGUSR2, SIGQUIT, SIGHUP, SIGXCPU, SIGXFSZ, SIGALRM) are saved with
      `sigaction` before the call and written back after it, with the nine blocked
      on the calling thread across the restore, in the same drop guard, before a
      stored panic resumes. The residual (a signal for another thread between the
      end of `clingo_main` and the restore) is documented, U38. The restore
      (`Containment::restore_signals`) runs the moment `clingo_main` returns,
      before the arena drain, the option closures and the script frame, so no
      user `Drop` runs with clasp's handler installed; `finish` keeps its failure
      and does the flush and the flag release later. The callbacks that run
      inside the call still run with the handlers installed. What is written
      back is the state saved at entry, so a disposition another thread changed
      during the run is overwritten (documented). A `sigaction` that fails while
      saving fails the run before `clingo_main` (`ErrorKind::Unknown`, flag
      released); one that fails while restoring is returned after the run, with
      the exit code in the message. POSIX allows neither for these valid signals. Restoring through
      glibc's `sigaction` adds `SA_RESTORER` to a disposition that had none.
    - **Flushing.** Rust's `stdout()` and `stderr()` and C stdio (`fflush(NULL)`)
      are flushed before and after, so output written earlier survives a `_exit`
      path and the two streams stay ordered (F13).
    - **Argument filter.** Any argument whose option name (after `--`, up to `=`) is
      a prefix of `fast-exit` of at least two letters is refused, wherever it
      stands; `--time-limit` is allowed and documented. The other exiting options
      (`raw::exit_options`) are checked twice: before clingo starts, with clingo's
      own one-letter aliases, and again inside the register callback, after the
      application's `register_options` ran and before clingo parses, with the
      aliases it registered added. Short options are scanned as clasp's
      `handleShortOpt` does: a flag letter goes on to the next letter, a letter
      with a value takes the rest of the argument (the next argument if a required
      value has none), an unknown letter ends the scan. The second check fails the
      register callback, so `run` returns `InvalidInput` and clingo never parses.
    - **One clasp-mode run.** `--mode=clasp` opens its input through a
      function-local static that is never reset (U51). A process-wide flag
      (`CLASP_MODE_STARTED`) is set when the arguments select `--mode=clasp` and clingo is about to parse them:
      at the end of the register callback once its re-check passed, or just before
      `clingo_main` when no `register_options` is set. A later run that selects it is
      refused before anything starts, even if the first failed later; a first run
      refused inside the register callback does not count.
    - **Callbacks.** They borrow from the caller for `'a` rather than being
      `'static`: `run` blocks until clingo and every thread it started are done, and
      the context lives on `run`'s stack frame. The logger is `FnMut + Send` under a
      mutex; its panic goes into a first-writer-wins slot in the context (never a
      `thread_local!`, the logger can run on a solver thread) and is resumed after
      cleanup. The `program_name` and `version` callbacks return pointers into
      `CString`s owned by the run and never NULL (NULL crashes clingo, F9); every
      callback `run` does not provide stays NULL so clingo uses its default.
    - The `_exit` paths cannot be contained and are documented on `run`, in the
      guide and in the known issues.
- **S19. The application's control.** The `main` callback of
  `Application::main` receives a control that clingo owns (`ClingoControl` is a
  member of `ClingoApp` and is freed after the callback returns), so it must never
  free it, and nothing may keep it, or anything derived from it, past the call.
  The rule is structural, enforced by the type system and not by a runtime check.
  - **The brand.** `ScopedControl<'r>` carries `PhantomData<fn(&'r ()) -> &'r ()>`,
    invariant in `'r`. The callback's bound is `for<'r> FnOnce(&mut ScopedControl<'r>,
    &[&str])`, so `'r` is an arbitrary lifetime that ends inside the call. Safe code
    cannot build a second `ScopedControl<'r>` for that `'r` (the constructors are on
    `ScopedControl<'static>`, the alias `Control`), so `mem::replace`, `mem::swap`
    and stashing in a static, a `thread_local!`, a `Box<dyn Any>` or a spawned
    thread are all lifetime errors (E0521). With a covariant brand the swap would
    compile and a borrowed control could be leaked with an open search; invariance
    is what closes it. Compile-fail tests: `tests/ui/application_main_*.rs`.
  - **Derived views.** `Statistics<'c>`, `SymbolicAtoms<'c>`, `Configuration<'c>`,
    `Backend<'c>`, `SolveHandle<'c>` and the rest hold `&'c ControlCore`, the
    private struct that `ScopedControl` wraps. Such a value is made from
    `&'c ScopedControl<'r>`, whose well-formedness requires `'r: 'c`; inside `main`
    `'r` ends in the call, so every `'c` does, and no view needs the brand itself.
  - **Ownership kind.** `ControlHandle` has an `owned` flag fixed at construction
    (`ControlHandle::borrowed` is `unsafe` and crate-private). A borrowed handle's
    `Drop` closes a recorded search, backend and program builder and detaches the
    `SolveSync` (as an owned one does), and then does not call
    `clingo_control_free`. The trampoline owns the borrowed control on its own
    stack and drops it inside the panic guard, so it is dropped on every path, before
    clingo tears the control down, and never by user code.
  - **Keep-alive arena.** clingo can still call a registered observer or propagator
    until its teardown, after the handle is gone. A borrowed handle therefore moves
    its observers and propagators into the run's `Arena` when it is dropped, and
    `run` drops the arena after `clingo_main` has returned (and by `Drop` on any
    other path). Backend writers keep no Rust state, and solve-event handlers need
    no arena because the handle's `Drop` closes the search, and with it the handler,
    before returning to clingo; the finish event that clingo would deliver in
    teardown is delivered by that `Drop`. No callback of a registered observer or
    propagator was seen after `main` returned in measurements; the arena is for the
    ones clingo does not promise not to make.
  - **Failure.** `main` returning `Err` stores the error, sets clingo's error state
    and returns `false`; clingo prints `*** ERROR: (clingo): <message>` and exits
    with 65, which `run` does not show (it returns the stored error). A panic is
    stored in the run's panic slot (first writer wins, the logger's included) and
    resumed after the process-wide state is restored. The closure is not `Send`; it
    runs only on the thread that called `run`, which the trampoline checks.
  - **The model printer.** `Application::print_model` installs a printer
    trampoline only when the setter was called, and only with a `main`
    (`print_model` without `main` is `InvalidInput` at `run`: the printer's model
    reads crash clasp, U40). The rules:
    - **Threads.** The closure is `Fn + Send + Sync + 'a`: clasp calls it on the
      solver thread that found the model under `propLock_`, so never two at once,
      but possibly while `main` runs. The trampoline checks no thread.
    - **The default printer** is lent as `&mut DefaultPrinter<'p>` for a `'p` the
      trampoline picks per call (`for<'p>` bound), so it cannot be kept. It is
      `!Send + !Sync` (marker `*mut u8`): clasp holds the C `stdout` lock for the
      whole print, so another thread calling it would deadlock against the
      printing thread.
    - **Never `false` to clingo.** An error, a panic (caught by
      `guard`), or a failing `print` is stored (error first writer wins in the
      run's error slot, panic in the panic slot; the panic is resumed first),
      the run's `printer_failed` flag is set, and the trampoline returns `true`.
      Later calls return `true` at once, running neither the closure nor the
      default printer. The search is interrupted through the `SolveSync` of the
      control `main` received (published by the `main` trampoline, and by the
      script `main` trampoline through the same `with_borrowed_control`), which
      delivers the interrupt only while a search is running, so it never reaches
      a later solve call (S13). A blocking search on a build without threads
      cannot be interrupted from inside; it finishes silently.
    - **Stdio.** `fflush(NULL)` before the closure; `print` flushes Rust's
      stdout, calls the default printer, and flushes C stdio; after the closure
      returns on every path both are flushed. This keeps `println!` and clingo's
      text in program order on a pipe (F13).
  - **`clingo_register_script`** is process-global and never frees before
    exit; see S20.
- **S20. Custom scripting languages.** `clingo_register_script` writes to a
  plain `std::vector` that grounding reads without a lock, and calls `call`,
  `callable` and `main` of the script struct without a null check (U41).
  - **The freeze invariant.** A process-global flag, `frozen`, lives in the same
    `Mutex` that serialises registration (`raw::script`). It is set by exactly one
    function, `raw::script::freeze`, called immediately before the first
    `clingo_control_new` (in `ControlHandle::new`, which every constructor goes
    through) and immediately before `clingo_main` (in `raw::application::run`,
    after the argument checks, so a run refused before clingo is reached leaves
    the registry open). It is set even if the call then fails, and never reset:
    clingo's own "has executed a block" flag is not either, and a live-control
    count would allow register, drop everything, register again while another
    thread holds a pointer in flight. Controls that clingo creates inside a run
    are covered by the run's freeze. `register` takes the mutex, so when `freeze`
    returns no registration is in flight and none will start. Controls made
    through `clingox-sys` directly are outside the guarantee. `version` takes the
    same mutex around `clingo_script_version`, which walks the vector a
    registration may reallocate.
  - **Registration.** NUL check, mutex, freeze, duplicate name, then the call.
    Every struct member except `free` is non-NULL; `free` is always NULL because
    it runs during static destruction, after Rust may be gone. The script is a
    leaked `Box<Box<dyn Script>>` and the version a leaked `CString`, both
    pointers kept in the registry's process-lifetime static (never read, never
    dropped) so they stay reachable when clingo's own registry vector is destroyed
    at exit and LeakSanitizer reports nothing, with no suppression; a refused
    script (or one clingo rejects) is dropped at once, an accepted one never.
  - **The exception to S8.** Script trampolines get the process-global script as
    their data, which cannot name a control or a call, so their errors and panics
    go into a **thread-local** slot. This rests on a measurement: script
    callbacks run only on the thread that called `add`, `load`, `ground` or
    `clingo_main`, never on a solver thread (`-t4` with sixteen models, a control
    on a spawned thread, `run` on a spawned thread). Every API call that can run
    script code (`add`, `load`, `ground`, `ground_with`, the program builder's
    `add`, `run`) opens a `ScriptFrame`: it saves and clears the slot, calls
    clingo, takes what the slot holds and restores the saved content, so a stale
    value cannot leak into the next call and a call made from inside a script
    callback (a `main` that adds to its control) does not mix with the outer one.
    Without an open frame on the thread nothing is stored (and clingo's own error
    still stops the call). The rest of S8 holds: `catch_unwind`, first writer
    wins, later callbacks return `false` at once without running user code, and
    clingo's copy of the error is never what the API reports.
  - **Poisoning.** An error from `execute` poisons whatever its kind (clingo
    keeps the rest of the failed program queued in its parser, and the next `add`
    or `load` would resume it: U44), does not pass through `add`'s `Runtime` to
    `Parse` remap, and is reported by `ControlCore::settle_scripts`. An error from
    `callable` or `call` poisons whatever its kind, like a failing ground
    callback. A panic poisons and resumes on the caller's thread.
  - **The script `main`** receives the run's borrowed control through
    `raw::application::with_borrowed_control`, the same lend-and-drop path as the
    application's `main` (S19), reading the run's arena from a thread-local set
    by `run`. Its error and panic go to the run's frame; `run` returns the error
    and resumes the panic after cleanup.
  - **Scripts and ground callbacks.** With a callback, clingo asks the callback
    first for every `@` term and never reaches a script; the callback wins for all
    names.

## 9. WebAssembly

The full API must work in the browser, so clingo's C++ and our Rust link into one
WASM module. The npm `clingo-wasm` package only offers "run a program, get JSON"
and cannot support callbacks, multi-shot solving or propagators.

**Target: `wasm32-unknown-emscripten`**, proven by the spike
on stable Rust with emsdk 6.0.10:
- clingo, a C test and the Rust test program pass under Node.js and in headless
  Chromium, including multi-shot solving with externals;
- clingo is compiled with **`-fwasm-exceptions`**, matching what stable Rust uses on
  this target. Without it the first clingo error aborts, and `-fexceptions` fails to
  link;
- a Rust panic in a callback, caught by `catch_unwind` and reported through
  `clingo_set_error`, comes back as an error and the process survives. A panic that
  unwinds into clingo's frames aborts, on native targets as well, which is why S8
  is mandatory;
- **no LTO on clingo's C++**: `-flto` breaks exception catching;
- size of the minimal program: 1.74 MB raw, 655 KB gzip, 489 KB brotli, plus 17 KB
  gzip of JS glue.
  Dead-code elimination removes only about 14% (1.98 MB with all 254 functions
  kept): 79% of functions are reachable through vtables, so the grounder and solver
  always stay;
- **threads** work with Emscripten pthreads, in Node.js and in Chromium on pages
  served with `Cross-Origin-Opener-Policy: same-origin` and
  `Cross-Origin-Embedder-Policy: require-corp`. 4 threads cut a test solve from 1611
  to 758 ms, for +1.3% size. This currently needs nightly Rust (`-Zbuild-std`,
  atomics), so the threaded WASM build is opt-in and follows stable Rust when that
  becomes possible. clingo's error state is `thread_local` there: its plain-global
  branch is guarded by `EMSCRIPTEN`, which emcc does not define (UPSTREAM-ISSUES U3,
  checked with emsdk 6.0.10).

The WASM default is therefore single-threaded (`threads` off), with a documented
threaded variant for cross-origin-isolated pages. WASI (`wasm32-wasip1`) works only
with a clingo patch, nightly Rust and a Node flag, and is 37% larger, so it is not
a supported target. `wasm32-unknown-unknown` cannot host clingo's C++.

CI runs the test suite under Node.js (debug and release) on every PR and one
headless-browser job nightly.

## 10. Versions over time

- **The version number carries clingo's version:** `MAJOR.MINOR.PATCH` =
  `{clingo major}{clingo minor, 2 digits}.{clingo patch}.{our release}`.

  | clingox | means |
  |---|---|
  | `508.2.0` | clingo 5.8.2, our first release for it |
  | `508.2.1` | clingo 5.8.2, our fix or additive release on top |
  | `508.3.0` | clingo 5.8.3 (compatible upgrade) |
  | `509.0.0` | clingo 5.9.0 (a new major, so Cargo never upgrades across it) |

  Precedent: `llvm-sys` (`231.0.0` = LLVM 23.1), `openssl-src` (`300.x` = OpenSSL 3),
  `z3-src` (`501.0.1` = Z3 5.1).
- **Why not plain `5.8.2`:** Cargo treats `5.8` → `5.9` as compatible, but clingo
  breaks its API in minor releases, so `cargo update` would break users. A plain
  copy would also leave no number for our own fixes.
- **All three crates share the number**, and each depends on the others with `=`.
  A change to one crate therefore republishes all three, as Microsoft's `windows`
  crates do. Additive features land in the last number, since the middle one is
  clingo's patch; users who need a feature pin at least that release.
- **The rule it imposes:** breaking changes to our own Rust API ship only with a new
  clingo minor version. Until the binding is complete, releases are pre-releases
  (`508.2.0-alpha.N`), where breaking changes are allowed.
- A clingo patch release maps to our next minor (`508.3.0`). If a patch release ever
  changes the C API (it has not happened; clingo's API breaks so far all came with
  minor releases), there is no free major to move to, because `509` belongs to
  clingo 5.9. So `clingox-sys` mirrors clingo and takes the change under `508.3.0`
  with a changelog warning, and `clingox` absorbs it internally so the safe API stays
  compatible.
- **Using another clingo version:** pick the clingox release whose number names it.
  A system library outside the accepted range is refused with a clear message.
- **Upgrade workflow:** a weekly job polls `potassco/clingo` releases. On a new tag a
  bot branch:
  - moves the submodule;
  - regenerates the bindings, whose diff is the API diff;
  - updates the version constant;
  - attaches the diff of `libclingo/tests` and `examples/c` between the two tags;
  - opens a PR.

  A person then wraps new functions, ports changed tests, updates COVERAGE.md and
  decides the version.

## 12. Decisions and changes

**Decided:**
1. The first release is `508.2.0`, only once the binding is complete.
2. Versioning follows §10.
3. All platforms, browsers included, with multi-threading wherever the platform
   allows it.

**Notable design decisions:**
- Propagators: one `&self` + `Send + Sync` trait instead of `Mutex` + `&mut self`,
  which would deadlock (S11).
- `for_each_model` runs on the caller's thread through the yield handle (S10).
- Solve-handle semantics corrected: `close` cancels, and `get` returns the result (S7).
- Errors: state reset before calls, value-returning `bool`s classified, void
  callbacks, `ErrorKind::Parse` with captured messages, callback errors recoverable
  (S1–S3, S8, S9).
- Interrupts: sticky semantics handled, and interrupt-vs-free locked (S13).
- Leftover handles finished by `&self` entry points too (S4).
- System clingo floor raised to 5.8.1; runtime check includes the patch (§5.1, S18).
- Link order `clingo gringo reify clasp potassco` (§5.2).
- The AST builder is called internally by typed constructors (S17).
- New pillars: determinism and resource limits (§2, §6.5); WASM in scope (§9).
- `clingo_main` and scripts isolated as process-global (S18).
