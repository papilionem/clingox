# Engineering rules

These rules apply to every change in this repository, whoever makes it. `DESIGN.md`
explains why the binding is shaped the way it is; this document says how we work
inside that shape. If the two ever disagree, fix whichever is wrong in the same
change. Do not leave them contradicting each other.

## 1. How a change is made

Every non-trivial change follows the same order:

1. **Contract.** Write down what the change must do, in the issue or at the top of
   the PR: which C functions, which behaviour, which safety rules (S1 to S20) apply.
2. **Acceptance tests first.** Write the tests that prove the contract, and run them
   to see them fail for the right reason.
3. **Implementation.**
4. **Verification.** Run the full local suite (see `TESTING.md`). Then apply the
   negative controls: break the new code on purpose and confirm that the new tests
   fail. A test that still passes against broken code is too weak and must be fixed
   before merging.

A change that cannot name its acceptance tests is not ready to be implemented.

## 2. Unsafe code

The whole point of this crate is to make clingo safe to use, so `unsafe` is held to
a higher standard than anything else. The aim is not zero `unsafe` (every call into
C is `unsafe` by definition) but **zero `unsafe` for users, and a small, audited,
contained amount for us.**

- **One module may contain it.** In `clingox`, only the private module `raw` (and its
  submodules) may contain `unsafe`. The crate root declares
  `#![deny(unsafe_code)]` and `raw` alone opts out with `#[allow(unsafe_code)]`, so
  the compiler rejects `unsafe` anywhere else: the typed layer, the conveniences, the
  code generated by `clingox-derive` (which must compile under
  `#![forbid(unsafe_code)]` in a user crate), and `clingox`'s own tests. Those tests
  declare `#![forbid(unsafe_code)]`, which proves the public API needs no `unsafe`.
  Nothing outside `raw` names `clingox_sys`.
- **A few primitives, reused everywhere.** Most clingo calls follow a handful of
  shapes. Each shape gets one small `unsafe` helper in `raw`, reviewed once, and the
  wrappers call the helpers instead of writing their own `unsafe` blocks:
  - `call(|| ffi::…)`: reset the error state, call, and turn a `false` into
    `Error` (DESIGN S1);
  - `fill_vec` and `fill_string`: the query-size-then-fill pattern (S17);
  - `c_str` and `borrowed_str`: C strings in and out, with the NUL and UTF-8 rules;
  - `raw_slice`: a pointer and length from C, null-safe;
  - the trampoline generator for callbacks (S8).

  A new `unsafe` block outside these helpers needs a reason in the PR that the
  helpers cannot express.
- **An `unsafe` budget.** `cargo xtask check` counts `unsafe` blocks and
  `unsafe impl`s outside the generated bindings and compares them with the number
  in `xtask/unsafe-budget`. A higher count fails the check until that file is
  updated in the same change, so every new `unsafe` is a visible decision in
  review. A lower count is reported so the budget can be lowered.
- **Verified, not only counted.** The `unsafe` code runs under Miri (the helpers and
  trampolines, with fake C data, `cargo xtask miri`), and the test suite under
  AddressSanitizer and LeakSanitizer and the thread tests under ThreadSanitizer
  (`cargo xtask sanitize`, TESTING §5).
- **Lints.** Both crates enable:

  ```rust
  #![deny(unsafe_op_in_unsafe_fn)]
  #![deny(clippy::undocumented_unsafe_blocks)]
  #![deny(clippy::missing_safety_doc)]
  ```

- **Every `unsafe` block carries a `SAFETY:` comment** that states the invariant it
  relies on and where that invariant comes from, usually a line in `clingo.h` or a
  rule in `DESIGN.md`:

  ```rust
  // SAFETY: `self.ptr` is non-null and owned (Control::new is the only
  // constructor). The call cannot run concurrently with a solve: S4 finishes
  // any leftover handle before we get here (clingo.h:2981).
  let ok = unsafe { ffi::clingo_control_ground(self.ptr.as_ptr(), ...) };
  ```

  "This is safe" is not a justification. Name the reason.
- **Never** `transmute` C enums or integers, fabricate `&mut` from a C pointer, call
  `slice::from_raw_parts` with a possibly null pointer, or let a panic cross an
  `extern "C"` boundary. Rules S8 and S17 in `DESIGN.md` give the required patterns.
- Every `unsafe fn` in our own code has a `# Safety` section in its rustdoc.

## 3. Wrapping a C function: definition of done

A clingo C function counts as wrapped only when all of these hold:

1. It has a safe Rust entry point, or `docs/dev/COVERAGE.md` explains why it is not
   exposed.
2. Its `bool` return is classified in COVERAGE.md as a success flag (goes through
   `check()`, S1) or a value.
3. Output parameters are allocated on the Rust side, and size-query-then-fill pairs
   are collapsed into one call (S17).
4. It has at least one test for the success path and, where the C function can fail,
   one for the failure path.
5. Its upstream test, if one exists in `libclingo/tests`, `libpyclingo` or
   `examples/c`, is ported (see `TESTING.md`).
6. Its public item has complete rustdoc (section 5).
7. The COVERAGE.md row is filled in: wrapper path, test path, notes.
8. If it adds or changes something users see, the user guide (`guide/`) covers it:
   the chapter for that area, a how-to guide if it serves a task, and the changelog.

## 4. API rules

- **Two layers, one crate.** Mirror-layer methods follow pyclingo's names. Typed-layer
  conveniences sit on top and never do anything the mirror layer cannot. When a
  convenience hides a clingo subtlety (as `add_facts` does with program parts), its
  docs say what it does underneath.
- **Add a convenience only when** it removes real boilerplate from a common task,
  or prevents a common mistake. Aesthetic wrappers are not added.
- **Naming** follows the Rust API Guidelines: `new` for the plain constructor,
  `builder()` for configuration, `as_`/`to_`/`into_` by cost and ownership, no `get_`
  prefix, `is_` for predicates. Deviations from pyclingo names are listed in the API
  docs.
- **Failure.** Anything that can fail returns `Result`. "Not this variant" returns
  `Option`. Library code never panics on bad input; `unwrap` and `expect` are allowed
  only where an invariant makes failure impossible, with a comment saying which.
- **Future-proofing** (required by the version policy, DESIGN §10): public enums are
  `#[non_exhaustive]`, public structs have private fields, extension traits are
  sealed. The `Result` alias is never glob-exported.
- **Thread and lifetime bounds** follow DESIGN S10 to S12 exactly. Relaxing a bound
  (for example making `Control: Send`) requires the test named in DESIGN §11 first.

## 5. Comments and documentation

**Code comments explain why, not what.** Good comments state an invariant, the
reason for a non-obvious choice, a link to the clingo behaviour being worked around,
or a `SAFETY:` justification. Remove comments that restate the code.

```rust
// Bad: copies the error message into a String.
let message = error_message_owned();

// Good: clingo overwrites this buffer on the next failure or message query on
// this thread, so it must be copied before any other clingo call (S1).
let message = error_message_owned();
```

- No commented-out code, no changelog comments ("changed on …"); git history keeps
  that. A `TODO` names an issue: `// TODO(#42): …`.

**Every public item has rustdoc** with:
- a one-line summary sentence;
- a short explanation when the behaviour is not obvious from the name;
- `# Errors` whenever it returns `Result`, listing the `ErrorKind`s it can produce;
- `# Panics` if it can panic, and `# Safety` for `unsafe fn`;
- an `# Examples` section for every entry point a user starts from. Examples are
  doctests and must run.
- Links use intra-doc syntax (``[`Control::ground`]``), never URLs to our own docs.

### User documentation

There are three places, each with one job:

- **rustdoc** (published on docs.rs) is the reference: every public item, with
  examples.
- **The guide** (`guide/`, an mdBook) teaches: getting started, the tutorial, how-to
  guides, concepts and reference tables. It follows the Diátaxis split, so a page is
  either a tutorial, a how-to, an explanation or a reference, never a mix.
- **The README** is the first page a visitor sees: what clingox is, how to install
  it, one short example, and links.

Every Rust code block in the guide and the README compiles and runs as a test.
A chapter is written together with the API it describes, never ahead of it.

## 6. Writing style

Everything in this repository (docs, READMEs, rustdoc, comments, commit messages)
should read as plain, professional writing.

- Short declarative sentences. Say what something does, then why if it matters.
- Avoid em-dashes; use a comma, a colon, parentheses or a new sentence.
- Avoid filler and hype: "robust", "seamless", "powerful", "simply", "it's worth
  noting", "in summary". If a claim matters, give the number or the source instead.
- Headings and table cells are fragments; body text is full sentences.

## 7. Dependencies and toolchain

- Add or upgrade dependencies only with the tools: `cargo add`, `cargo upgrade`
  (cargo-edit), `cargo update`. Never type a version number by hand. The same applies
  to `npm install` for any JavaScript tooling.
- Every new dependency is justified in the PR: what it gives us, and why the standard
  library or an existing dependency does not.
- `cargo deny check` must pass (licenses compatible with MIT OR Apache-2.0, no known
  advisories, no duplicate major versions without a reason).
- **MSRV** is the latest stable Rust (DESIGN §8.3). Raising it is a normal change,
  noted in the changelog.
- Edition 2024; move to a new edition with `cargo fix --edition` when one ships.

## 8. Build rules for the native code

These encode lessons that were expensive to learn. Do not change them without a test
that proves the new setting.

- The vendored clingo source under `clingox-sys/clingo` is **never edited**. It must
  match the upstream tag byte for byte (the commit-hash check enforces this).
- **Upstream bugs clingox cannot fix from Rust** are fixed by a small patch set in
  `clingox-sys/patches/`, applied at build time to a copy of the source, never to
  the submodule (decided 2026-09-27). Each patch:
  - fixes exactly one entry in `docs/dev/UPSTREAM-ISSUES.md`, whose number starts
    its file name (`U1-division-traps.patch`);
  - has a test that fails without it;
  - is as small as possible and suitable for sending upstream.

  Only vendored builds get the patches. A system library does not, and the docs
  say so. A patch is removed when the clingo release that clingox binds contains
  the fix, and UPGRADING §1.5 checks this on every upgrade.
- All five static libraries are linked: `clingo gringo reify clasp potassco`.
  (Their order does not matter, because Rust bundles them into one archive.)
- Never enable LTO on clingo's C++: it breaks exception catching (found in the WebAssembly spike).
- On `wasm32-unknown-emscripten`, clingo is compiled with `-fwasm-exceptions`.
- Bison and re2c are disabled so the committed parsers are used.
- System clingo is accepted only for `>= 5.8.1, < 5.9.0`.

## 9. Commits and branches

- One logical change per commit. Refactors and behaviour changes go in separate
  commits.
- Subject line: `Area: imperative summary`, at most 72 characters, no trailing period
  (`Symbols: add checked tuple constructor`). Areas in use: `Build`, `Sys`,
  `Raw`, `Control`, `Solve`, `Model`, `Externals`, `Symbols`, `Errors`, `Propagate`,
  `Ast`, `Derive`, `Testing`, `Tests`, `Guide`, `Docs`, `Design`, `Xtask`.
- The body explains why, not what, wrapped at 72 characters.
- `main` always builds and passes the local suite. Work happens on branches named
  `area/short-description`.

## 10. Review checklist

Before merging, the reviewer confirms:

- [ ] The contract is stated and the acceptance tests match it.
- [ ] Negative controls were run and every new test failed against broken code.
- [ ] Every `unsafe` block has a specific `SAFETY:` comment.
- [ ] The applicable DESIGN rules (S1 to S20) are respected; any relaxation has its
      proving test.
- [ ] COVERAGE.md is updated for every wrapped function.
- [ ] Public items have complete rustdoc, and examples run.
- [ ] No new `unsafe` outside `raw`; any change to the `unsafe` budget is explained.
- [ ] Errors carry context, `Debug` output is useful, nothing panics on caller
      input, and `#[must_use]` is on values that are easy to drop by mistake (§11).
- [ ] `cargo xtask check` passes: fmt, clippy, docs, tests, deny, unsafe budget.
- [ ] Wording follows section 6, and commits follow section 9.

## 11. Rust idioms

clingox should feel like a Rust library written by people who know Rust well, not
like C with Rust syntax. This section collects the practices that make that true.

### 11.1 Errors

- There is one error type, `clingox::Error`, modelled on `std::io::Error`: a
  `kind()` for matching, a message for people, and `source()` for the cause
  (DESIGN S2). It is `Send + Sync + 'static`, which a compile-time assertion checks.
- **Errors carry context.** The message names the operation and its subject
  ("grounding part `step(3)`: …", "parsing program `base`, line 4: …"), not just
  clingo's text. Parse errors carry every captured clingo message with its location.
- `Display` is one line: lowercase, no trailing period, as the standard library
  does. `Debug` shows everything: kind, message, captured messages, source chain.
- **The cause is never lost.** User errors from callbacks keep their original type,
  reachable through `source()` and `downcast_ref`. A panic in a callback resumes as
  a panic; it is not flattened into a string.
- No catch-all conversions such as `From<String> for Error`. Errors come from
  clingo, from our own checks, or through `Error::callback(e)`.
- The alias is `clingox::Result<T, E = Error>`, and it is never glob-exported.

### 11.2 Panics

- **No public function panics on input a caller can supply.** Bad input is an
  `Err`. A panic in clingox means a bug in clingox.
- `unwrap` and `expect` in library code are allowed only where an invariant makes
  failure impossible. `expect` messages state the invariant ("clingo returned a
  null model while the handle reported one"), and a comment says why it holds.
- A public function that can panic documents it under `# Panics` and is marked
  `#[track_caller]`, so the panic message points at the caller's line.
- Panics in user callbacks are caught and resumed on the caller's thread (S8).
  After a resumed panic the `Control` stays usable (S3). `Drop` never panics (S13).
- **`panic = "abort"`.** When a user builds with `panic = "abort"`, there is no
  unwinding, so a panic in a callback aborts the process where it happens. That is
  sound, and the docs say so. It is tested with a separate crate built that way.

### 11.3 Debugging and observability

- **Every public type implements `Debug`, and the output is useful.** It shows what a
  developer needs, never only a pointer value:
  - `Symbol` prints as `Symbol(p(1,"x"))`, not as its 64-bit handle;
  - `Model` shows its number, cost and atoms;
  - `Control` shows its state (idle, solving, poisoned) and what is registered on
    it;
  - `Error` shows everything listed in 11.1.
- `Display` is implemented wherever clingo has a canonical text form: `Symbol`,
  `Signature`, `Model`, `SolveResult`, `Location`, `Error`, `ErrorKind`.
- **`debug_assert!` guards internal invariants** that are cheap to check and costly
  to debug when broken: pointers clingo must not return null, sizes that must match,
  state transitions of the `Control`. They cost nothing in release builds.
- **No printing from library code.** clingo's messages go to the `log` crate (target
  `clingox`, feature `log`) or to the user's logger. With the feature `tracing`,
  `add`, `ground` and `solve` open spans with the program part and duration.

### 11.4 Types and traits

- **Standard traits wherever they make sense** (Rust API Guidelines C-COMMON-TRAITS):
  `Clone`, `Copy` for small values such as `Symbol`, `PartialEq`/`Eq`/`Hash`,
  `PartialOrd`/`Ord` using clingo's own order, `Default` where a sensible default
  exists, `FromStr` for `Symbol` and `Signature`, `From`/`TryFrom` conversions,
  `IntoIterator` for collections. Whether a public type is `Send` or `Sync` is
  decided by DESIGN S12, and asserted at compile time.
- **Flexible inputs.** Accept `impl AsRef<str>`, `impl AsRef<Path>` and
  `impl IntoIterator<Item = …>` rather than one concrete type.
- **Honest outputs.** Return an iterator when the data can be produced lazily and
  borrowed, and an owned `Vec` or `String` when it must outlive a borrow.
- **`#[must_use]`** on values that are easy to drop by mistake: solve handles,
  backend and builder guards, builders, `SolveResult`, and functions that return a
  new value without side effects (symbol constructors).
- Newtypes for separate id spaces, enums instead of `bool` parameters, and
  clingox's own newtypes over clingo's bits for flag sets, with `|`, `|=` and
  `contains`, as `ShowType` is (S17); no flag-set crate in the public API. Traits that users should not implement are sealed.
- Typestate (encoding a state in the type) only where it prevents a real mistake at
  compile time without making common code awkward.

### 11.5 Macros

- **Use a function when a function works.** A macro is justified only when it buys
  something a function cannot:
  - `sym!` accepts clingo term syntax;
  - the derives generate conversions from a type definition;
  - test macros such as `assert_models!` report the caller's line and a readable
    diff.
- Procedural macros live in `clingox-derive`. Their generated code goes through
  `::clingox::__private`, contains no `unsafe`, and compiles in a crate that forbids
  `unsafe_code`. Their errors point at the user's code (`syn::Error::new_spanned`),
  and trybuild tests pin those messages.
- `macro_rules!` inside the crate may remove mechanical repetition, such as enum
  conversions generated from the binding constants. It must not hide control flow
  or `unsafe`.

### 11.6 Lints

The workspace `[lints]` table in `Cargo.toml` enables, for all crates:

- rustc: `missing_docs`, `missing_debug_implementations`, `unreachable_pub`,
  `unsafe_op_in_unsafe_fn`;
- clippy: `pedantic` (each allowed pedantic lint listed with a reason),
  `undocumented_unsafe_blocks`, `missing_safety_doc`, `print_stdout`,
  `print_stderr`, `dbg_macro`, `todo`, `unwrap_used` (allowed in tests).

Generated bindings in `clingox-sys` opt out of the documentation and naming lints,
with a comment saying why.
